# Free Soar 流程走查

目的：在真人測試**之前**，用固定的方法把一條流程裡「看不懂、找不到、不確定成功沒」的地方先找出來，並檢查網站有沒有涵蓋這個角色平常真的要做的事。每次做法一樣，結果才能互相比較。

這個 skill 只讀程式。唯一會寫的檔案是第 5 步那份報告（放在 `docs/` 底下）；程式、設定、測試、其他文件都不改。改不改、先改哪個，由產品主人決定，之後走 AGENTS.md 的 spec → plan 流程。

## 第 0 步：確認範圍（一句話就好）

從使用者的話判斷兩件事，缺哪個才問：

- **角色**：老師／學員／團主／管理員
- **流程的起點和終點**：例如「從看到老師說明頁 → 第一堂課有人報名」

如果使用者只說「老師的流程」，預設走「第一次加入」這條（從發現入口到完成第一個有價值的結果），因為第一次使用最能看出流程能不能自學。

## 第 1 步：先讀既有紀錄，不要重做

到 `docs/superpowers/plans/` 找同角色的舊走查、flow map、handoff（例如 `teacher-experience-walkthrough/`、`entry-and-sign-in-flow-review/`），還有 `docs/backlog.md`、`docs/context/glossary.md`。舊紀錄已經記下的問題，在新報告裡引用就好，不要當成新發現；嚴重度沿用舊紀錄，舊紀錄沒寫就填「沿用，未評」。

同主題已有舊的走查報告時，先讀它，再照第 2 步重新查程式：程式可能已經改了，舊結論不能直接照抄。新報告另存一份新日期的檔案，不覆蓋舊的，並在開頭寫「與上次相比」：哪些已解決、哪些還在、哪些是新發現。

## 第 2 步：畫路線（從程式找，不要用猜的）

列出這條流程實際經過的每一頁和每個分岔：route、要按的按鈕、會出現的通知或 email、各種狀態下畫面的差異（例如審核中、被退回、還沒有資料的空畫面）。

**每一步都要附依據**（檔案路徑，必要時加函式名）。報告裡任何關於「現在網站會怎樣」的說法，都要能在程式裡找到出處。上一次走查有兩個錯誤，就是沒查程式、憑印象寫出來的：一次把已經公開的期班寫成「不公開」，一次把只存在畫面上的「已複製」當成資料庫有紀錄。

特別要看的地方（最常出問題）：

- **空狀態**：第一次來、還沒有任何資料時，畫面上有沒有「下一步」
- **通知與 email 的文案和連結**：會帶人去哪一頁，那一頁在這個時間點有沒有東西
- **狀態轉換的時刻**：送出、審核通過、被退回、取消之後，使用者會看到什麼
- **登入前後**：登入完會回到哪裡（`callbackUrl`、`fsy_last_role`）
- **另一方做了事，這個角色會不會知道**：例如學員報名時老師有沒有收到通知、團主選定老師時老師看不看得到。要讀通知的收件人清單（`notifyUsers` 呼叫的 recipients），不要只看文案。只有一方收到通知，是很容易漏掉的問題
- **預設值對下一個角色的影響**：例如老師建課時的預設公開設定，會決定學員點連結時看到什麼。這種問題要沿著流程走到下一個角色的畫面才看得到

## 第 3 步：persona 走查

從 `references/personas.md` 拿這個角色的 3 位 persona。每位 persona 把路線從頭走一次，**每一步**都問這 4 個問題（cognitive walkthrough 的標準問題）：

1. **知道現在該做什麼嗎？**（目標清不清楚）
2. **看得到要按哪裡嗎？**（入口能不能被發現）
3. **看得懂按了會怎樣嗎？**（標籤和文案能不能對上他的目標）
4. **做完知道成功了嗎？**（有沒有回饋、下一步）

不需要把「3 位 × 4 題 × 每一步」的表格全部寫出來。每位 persona 從頭走一次，只記**答案是「不」的地方**：哪位 persona、哪一步、哪一題（Q1–Q4）、為什麼會卡。不同 persona 卡在同一處，代表問題更嚴重。persona 的「容易卡在」欄位，是提醒你走到哪幾步要特別仔細看。

第一次使用的流程，另外用 `.claude/skills/impeccable/reference/onboard.md` 的原則檢查（time to value：多快拿到第一個有價值的結果、空狀態有沒有說明「這裡會出現什麼、為什麼重要、怎麼開始」）。

需要對照公認原則時，用 `.claude/skills/impeccable/reference/critique.md` 裡的 Nielsen 10 條：只讀 `### Heuristics Scoring Guide` 這一段（用 Grep 找標題），其他打分流程跟這裡無關。只引用真的違反的原則，不用 10 條全部打分數；完整打分是 `/impeccable critique` 的工作。

## 第 4 步：日常工作對照

從 `references/jobs.md` 拿這個角色的日常工作清單，每一項對照程式，標「有／部分／沒有」，並附依據。

- 「沒有」的項目**不等於要做**。jobs.md 每項已標好 V1 狀態，照著寫：「V1 不做」的標「超出 V1」；「未定」的標「需產品主人決策」。
- 判斷「有沒有」要查到實際行為，例如付款只是手動標記、不是金流，就寫「部分」並說明。

## 第 5 步：寫報告

用 `references/report-template.md` 的格式，存到 `docs/superpowers/plans/<角色與流程的英文 kebab-case>-walkthrough/review.md`（已有同主題資料夾就放進去）。內容用繁體中文。

寫報告時遵守：

- **嚴重度**：高＝會讓人放棄或走錯方向，且多位 persona 都會卡；中＝會猶豫、要繞路，但還走得下去；低＝看起來怪，但不影響完成。
- **每條結論都標「待驗證」**，除非有在瀏覽器實際看過那個畫面。報告開頭要寫清楚這次有沒有實際操作、為什麼。
- **建議要標來源**：是 skill 指示的方法（例如「依 onboard.md 的 time to value 原則」），還是 Claude 自己的判斷。產品主人需要分辨兩者。
- **會動到 Auth、Prisma schema、權限、狀態機、V1 scope 的建議**，一律標「需產品主人決策」，不要寫得像已經決定。
- **建議只能用現有資料做到的，才寫成「只改畫面」**。如果某個勾選、計數或狀態沒有資料可判斷（例如只存在 React state），要明講，並提出不用新資料的替代做法。
- **建議要在某個動作前提醒或攔一下時，列出所有能觸發這個動作的入口**（例如「開放報名」有單堂按鈕、建立時直接開放、系列全部開放、單場快速開放）。只改一個入口，其他路徑仍會照舊。通知類建議也要寫清楚「點了會到哪一頁」，而且要依收件人分別處理。
- 真人測試腳本 5–7 題，每題對應至少一個發現，先驗「懂不懂」再驗「會不會操作」，不要在題目裡把答案講出來。

報告寫在 `docs/superpowers/plans/` 底下，Stop hook 會要求 `codex-peer-review`。照那個 skill 跑完，Codex 抓到的錯誤直接修進報告。如果呼叫你的人指定了別的存放位置，或說明跳過 Codex，照他的指示。

## 第 6 步：回報與下一步

在對話裡用白話總結：最重要的 3 個發現、日常工作對照的一句結論、建議。然後最多給兩個下一步選項，通常是：

1. 把高嚴重度的發現寫成 spec（走 AGENTS.md 流程）
2. 先用報告裡的測試腳本找真人測試

如果有 1–3 個頁面同時有好幾個發現，可以提議再對那幾頁跑 `/impeccable critique <頁面檔案>`，補上視覺與版面的檢查。它需要瀏覽器，也比較花時間，所以只提議、等使用者同意再跑。

## 不要做的事

- 不改程式、不寫 migration、不 commit。
- 不在瀏覽器替使用者登入。需要登入後的畫面，請產品主人自己登入；做不到就只讀程式，並在報告開頭註明。
- 不寫假資料進資料庫來製造畫面狀態。
- 不把 persona 的推測寫成「使用者會這樣」。persona 是用來找問題的工具，真人測試才是證據。
