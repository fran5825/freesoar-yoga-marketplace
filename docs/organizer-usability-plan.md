## 第二輪 usability 訪談（2026-10-03，進行中）

本輪使用 `/grill-with-docs`（`grilling`＋`domain-modeling`），目標是讓團主註冊、提出需求、成立課程與全站入口形成連續且清楚的使用流程。第一輪定案保留為歷史；本節未確認的提案不取代既有決策，也不代表已實作。

### 已查證現況與資訊斷點

- `/organizers/request`：訪客先登入，沒有團主資料的人前往建立資料；已有團主資料的人直接導向 `/organizer/demands/new`。介紹頁仍說只需顯示名稱與所屬組織，但註冊表單實際包含顯示名稱、團體名稱／類型、聯絡窗口姓名／信箱／電話。
- 介紹頁三步驟停在「等待平台審核」，沒有完整說明老師回應、團主選老師、成立課程與學員報名的後續路徑。
- `/organizer/profile` 同時承擔第一次建立團主資料與之後編輯資料。建立成功預設前往新需求表單；編輯若帶合法 `next` 則返回指定的團主頁面。
- `/organizer/demands/new` 的草稿 ID 與填寫內容保存在 client state；儲存草稿成功後網址仍是 new。補資料連結的 `next` 固定回 new，因此即使儲存過草稿，返回 new 也不會自動載入該筆草稿；未儲存的變更同樣無法恢復。這比第一輪「先儲存草稿即可返回」的敘述更嚴重，需補齊草稿與返回路徑設計。
- `OrganizerShell` 現在沒有新增需求 CTA；「＋ 發起新需求」位於我的需求列表底部，空列表另有建立入口。名詞表已收錄「建立入口放清單最底」，不能把舊計畫的右上固定 CTA 當成現況。
- 目前資料模型仍是一個帳號至多一個團主資料、一個團主至多一個團體。建立團主資料不需事先審核；需求送審需要完整聯絡資料。多團體仍是另列範圍，不能因「建團」一詞直接視為已授權。
- V1 老師回應不會把需求寫成 `teacher_responded`；實際為 `published → matched → converted_to_class`。流程提示需依回應資料推導，不能靠保留 enum 假設功能已接線。

### 老師能否建團：已查證能力與待選方案

- 現有 capability model 允許同一個 `User` 同時擁有老師與團主資料，不需要建立第二個帳號。`createOwnOrganizerProfileWithOrganization()` 只要求 signed-in user，沒有排除老師或要求老師先通過審核。
- 還沒有團主資料的老師，角色切換中已有「＋ 成為團主」，連到 `/organizers/request`；建立團主資料後可切換團主專區。這回答的是「老師這個人也可以建團」，不代表 `TeacherProfile` 自動具有團體管理權限。
- 目前老師身分自建的「老師開課」與團主透過需求、選定老師後成立的「團主團課」是不同來源。現行團主建課 service 要求自己的需求處於 `matched`；沒有任意指定老師直接建課的團主路徑。開團是否仍需先找老師，須由 Q6 決定。

### 開團的兩條路徑（設計定案，尚未實作）

1. **需要找老師**：選團體 → 整理需求 → 平台審核 → 老師回應 → 團主選老師 → 成立課程 → 開放報名。
2. **已有合作老師**：選團體 → 選平台已通過審核的老師並填課程資訊 → 送合作邀請 → 老師確認 → 團主開放報名 → 分享連結。不再逐課平台審核。本人亦為已審核老師時，可選自己授課並明確確認，不需跨身分接受自己的邀請。

第二條是明確授權討論的新核心流程，不能假裝是既有 `matched` 需求轉課，也不能把 `Enrollment` 的學員報名確認視為老師同意授課。本輪先記錄設計方向；Prisma schema、permission、state machine、API 及相關 domain docs 待細節達成共同理解後，取得具體確認再同步與實作。

### 直接開團目前的模型與流程邊界

- `ClassSessionOrigin` 現在只有 `organizer_matched` 與 `teacher_initiated`；前者要求需求、團主、團體的關聯同時存在，後者要求三者同時為 null。已有老師直接開團不符合任一既有來源定義；需正式決定新來源／關聯不變量，不能沿用任一值讓 UI 與 service 誤判。
- 團主建課目前要求 own demand 是 `matched` 且已有 selected response；不能僅放寬頁面按鈕而略過 service 守衛。
- `ClassSession.pending_confirmation` 現在只有保留 enum，尚無老師確認授課的 transition。老師確認學員報名屬 `Enrollment`，不能用來代替授課合作確認。
- 現有排課衝突工具將非 cancelled 的課程都算入，包含 `draft`。若把待老師確認的邀請直接存成課程草稿，就會先占老師時段；需在 Q8 後決定何時正式占用時段，以及確認時如何檢查衝突。
- 尚未找到團主可用的老師搜尋 service；既有老師列表是 admin-only，不能直接挪給團主。新直接路徑需定義可見的老師名片資料與選取資格。
- 現有需求回應沒有比對老師與團主是否同一個 `User` 的 self-response 禁止守衛。不能把「老師不能選自己」當成既有規則；新直接路徑的自授課情境須明確決策。
- 公開課程查詢要求 `isPublic=true` 且符合公開狀態／老師資格；已登入的學員另有直接連結查看路徑。匿名訪客開非公開課程連結現在會是 not-found，需依 Q9 的曝光定案設計能辨識下一步、但不洩露私有資料的登入引導。
