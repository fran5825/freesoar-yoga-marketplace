# 第一次加入的老師：流程檢視（2026-10-24）

產品主人的目標：先從老師群開始開發。老師只要有這一個網站，就能管理日常教學業務；每個環節都讓老師不用教、自然學會。

這份是**只讀程式**整理出來的檢視，**沒有改任何程式**，也還沒在瀏覽器實際操作（當時開發伺服器沒開，登入要產品主人本人）。結論都標「待驗證」，要靠下方的真人測試確認。

用了兩個方法：

1. **cognitive walkthrough（認知走查）**：用 3 個老師 persona，每一步問四個問題：知道現在該做什麼嗎？看得到要按哪裡嗎？看得懂按了會怎樣嗎？做完知道成功了嗎？
2. **jobs-to-be-done（老師的日常工作清單）**：列出老師平常真的要做的事，對照網站做到了沒有。

## 第一次加入的路線（照程式整理）

1. 首頁小字「你是瑜伽老師？了解如何加入」或導覽「老師合作」→ `/teachers/join` 說明頁
2. Google 登入 → 同一頁變成申請表單（7 項必填）→ 送審
3. 審核中：唯讀摘要，等通知
4. 通過：站內通知＋email「現在可以開始回應需求了」，連到 `/teacher/profile`（可授課時間）
5. 第一次進 `/teacher/dashboard`
6. 補資料：照片、收款與聯絡、可授課時間
7. `/teacher/classes/new` 開第一堂課 → 詳情頁開放報名 → 複製報名連結／分享範本
8. 學員報名 → 確認／婉拒、標記已付款
9. 上課後標記完成 → 學員收到評價邀請
10. `/teacher/demands` 需求池回應團主

讀法：「用一個網站管日常教學」的核心（開課、招生、報名、補課、行事曆）已經具備。**主要的問題是老師進來之後不知道從哪裡開始，介紹頁也沒講出這個賣點**，不是功能不夠。標「沒有」的項目要等真人測試確認老師真的需要，才考慮要不要納入 V1。

## 建議（Claude 的判斷，不是 skill 指示）

1. **先修第一次使用的體驗（F1、F2、F3、F6）**：在總覽加一張「新老師上手清單」。這是 Shopify、Stripe 等平台常用的 onboarding checklist（上手清單，像新手任務一格一格打勾）：
   - 上傳照片
   - 填收款與聯絡方式
   - 開第一堂課
   - 開放報名

   每格依現有資料自動打勾（例如有沒有照片、有沒有填收款資訊、有沒有課程、有沒有開放報名的課），全部完成就收起來。「分享報名連結」**不放進會打勾的項目**：現在複製連結只記在當頁畫面（`CopyEnrollLinkButton.tsx`、`ShareTemplates.tsx` 的 React state），資料庫沒有分享紀錄，複製也不代表真的傳給學員。改成「開放報名」那格完成後出現的提示，帶到詳情頁的分享區。若之後要追蹤分享，要另外定義「完成」的意思和存放方式，屬於另一個決策。同時改通過通知的文案和連結，以及說明頁的主訴求。只動畫面和文案，不動 schema、權限、狀態機；仍照 spec → plan 流程，由產品主人核准。可用 `/impeccable` 的 onboarding 模式做設計。
2. **再找 3–5 位真的老師做 usability testing**，用下面的腳本。
3. F4（審核前試用）、F5（LINE 登入）、「沒有」的功能，等測試結果再決定。這些會動到權限、Auth 或 V1 scope，需要產品主人決策。

## 真人測試腳本（每人約 20 分鐘，只觀察、不教）

開場：「我們測的是網站，不是你。想到什麼就說出來，卡住也是很有用的資料。」

1. 「你聽朋友說有這個網站。看完說明頁，用一句話告訴我它能幫你做什麼。」→ 驗 F3
2. 「請申請成為老師。」（可先用測試帳號跳過審核）→ 記下停頓最久的欄位
3. 「審核通過了。你現在第一件想做的事是什麼？請去做。」→ 驗 F1、F2
4. 「開一堂下週四晚上的課，然後把報名連結傳給你的學員。」→ 驗開課與分享
5. 先指著一筆還沒付款的報名問：「這位學員的錢現在在哪裡？他要怎麼付給你？」聽完再說：「他剛剛轉帳給你了，請把這件事記下來。」→ 驗 F7（先驗理解，再驗操作）
6. 學員端：請受測者用另一支手機（或請一位朋友）打開第 4 題傳出的報名連結，從 Google 登入到完成報名。→ 驗 F5，記下在哪一步猶豫
7. 結束問：「如果明天開始只能用這個網站管你的課，你最擔心少了什麼？」→ 驗日常工作對照表

每題記：有沒有完成、花多久、在哪裡停下來、說了什麼原話。
