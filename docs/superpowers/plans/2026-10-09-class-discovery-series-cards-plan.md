# 找課程列表：系列卡合併 Plan

建立日期：2026-10-09。來源：產品主人在 `/classes` 看到同一門持續開課逐場重複出現、難以瀏覽，經 grill 討論（Q1–Q11）全部定案。

## 1. 問題

`/classes` 目前只有期班（`kind = term`）合併成一張卡，持續開課（`kind = continuous`）仍然逐場一張卡（`getPublicClassListEntries` 只把 term 收成一張）。同一門每週課開 8 週，列表就出現 8 張幾乎一樣的卡，學員很難比較不同的課。

## 2. 已確認決策

| # | 決策 |
|---|------|
| D1 | 持續開課與期班都合併成「系列卡」，一個系列一張；沒有系列的單堂課維持一場一張 |
| D2 | 系列卡只放：來源標籤（老師開課／團主團課）、標題、老師與課程風格、一行規律（每週四 19:00）、地點、瑜伽類型、下一個有名額的場次。拿掉「確認送出後成立報名」「查看課程 →」與綠色「開放報名」標籤，整張卡可點 |
| D3 | 持續開課新增詳細頁 `/classes/series/[recurringClassSeriesId]`：課程資訊、課程說明、適合對象、準備事項，加最近 8 堂場次清單與「看更多日期」；沒有整期報名；點日期進單堂頁報名。期班繼續用 `/classes/terms/[id]`，不動 |
| D4 | 持續開課卡的「下一堂」＝第一個還有名額的場次；篩選勾「包含已額滿」時改為最近一場並標額滿。**期班卡不適用**：期班維持現狀（下一堂＝符合篩選的最近一場；是否顯示依「整期能否報名」或單堂有空位的既有規則），因為只收整期的期班不能單堂報名，「有名額的場次」對它沒有意義 |
| D5 | 持續開課卡不顯示堂數（場次由系統往後生成，數字會誤導）；期班卡維持「共 N 堂・剩 N 堂」 |
| D6 | 系列只剩一場仍顯示為系列卡 |
| D7 | 頁首改「找到 N 個課程」（N＝卡片數）；卡片依「下一堂日期」由近到遠 |
| D8 | 日期、時段、地點、類型篩選以系列為單位：**持續開課**系列內任一場符合（且依 D4 有名額，或已勾包含額滿）就出現一張卡，「下一堂」為符合條件的那一場；**期班沿用既有行為，不適用** |
| D9 | 這輪不做排序／分組功能，篩選欄位不動 |
| D10 | 期班卡同樣拿掉「查看期班 →」行，讓兩種卡長相一致 |
| D11 | 不改 schema、權限、state machine；公開可見規則沿用現有（isPublic、狀態、老師 `approved`） |

## 3. 不在這輪範圍

- 排序、分組（依老師、依星期幾）。
- 期班頁（`/classes/terms/[id]`）的內容與整期報名流程。
- 單堂課頁的內容（它已列出同系列其他場次，沿用）。
- 付款、候補、通知、任何 V1 範圍外功能。

## 4. 設計

### 4.1 Service layer（`src/domain/class-session/public-read-service.ts`）

- `PublicClassListEntry` 新增 `kind: "series"`，內含 `PublicSeriesListItem`：`id`、`title`、`origin`、`teacherProfile`、`serviceTypes`、`yogaStyles`、`location`、`scheduleLabel`、`nextStartAt`、`nextSessionId`、`nextRemainingSeats`、`nextIsFull`、`requiresApproval`。不帶任何內部關聯 id。
- `getPublicClassListEntries`：把 `recurringClassSeries` 不為 null 的場次依系列歸組；`term` 走既有期班路徑（行為不變，見 D4），只有 `continuous` 走新的系列路徑。「下一堂」依 D4／D8 在已篩選的場次裡挑。
- 新增 `getPublicSeriesDetail(recurringClassSeriesId, { show })`：回傳系列資訊與公開可見的未來場次（含每場剩餘名額）；沒有任何公開可見場次或不是 `continuous` 一律回 `null`（not-found 語意，不揭露存在性）。
  - **分頁在 service 查詢層處理**：`show` 預設 8，每按一次「看更多日期」加 8（網址參數 `?show=16`），上限 200（只是防呆，實務上持續開課一般不會累積到這個數量；無效、負數或非數字的值退回預設 8）；查詢多取 1 筆判斷是否還有更多（`hasMore`），到達上限時不再顯示「看更多日期」，改顯示「僅列出前 200 堂」。每筆只取日期、時間、地點與報名人數，讀取成本固定很小，不先讀取全部場次。以「同一個 `show` 值總是回傳前 N 場」的方式分頁，不用 offset，跨次點擊不會重複或漏場次。
  - **課程資訊的資料來源**：標題、說明、適合對象、準備事項、地點、時間、老師，取自「第一個還有名額的未來公開場次；全部額滿時取最近一場並標額滿」，不用系列預設值。詳細頁沒有篩選條件，所以永遠用這條預設規則；卡片在預設狀態與它同一場，勾「包含已額滿」時卡片改顯示最近一場，兩者可能不同場，這是已接受的邊角情況，測試要涵蓋（標頭仍正確屬於它所指的那一場，不會混用兩場的資料）。因為「改這場和之後所有場次」只改所選場次以後的紀錄，系列預設值可能與近期可報名的場次不一致。場次清單每一列顯示自己的日期、時間、剩餘名額；若某場的地點或時間與標頭不同，該列加註實際地點／時間。
- 規律文字的組字沿用期班卡既有的 `scheduleLabel` 寫法，抽成共用函式，避免兩處各寫一份。

### 4.2 UI

- `src/app/classes/page.tsx`：新增 `SeriesCard`；`SessionCard` 與 `TermCard` 依 D2、D10 精簡；頁首文字依 D7。
- 新頁 `src/app/classes/series/[recurringClassSeriesId]/page.tsx`：版型比照期班頁（返回列表、標題、課程資訊、場次清單、說明區塊），但沒有報名面板。未登入訪客同樣可看，報名在單堂頁完成。
- 單堂頁的「同系列其他場次」若有連到系列的需求，只加一條連到新頁的連結，不改它的報名邏輯。

### 4.3 App-readiness

資料全部經 service layer 輸出，頁面只負責排版；沒有新增只給網頁用的邏輯。

## 5. 測試

- Vitest：期班行為不變（含 `term_only` 有名額場次但整期不可報時的既有結果）、歸組（持續開課 N 場 → 1 張卡）、下一堂選擇（含額滿、含「包含已額滿」）、篩選以系列為單位、單堂不受影響、只剩一場仍為系列卡、`getPublicSeriesDetail` 的可見規則與 not-found、`show` 分頁（前 N 場、`hasMore`、不重複不漏、無效值退回預設、到達 200 上限的提示）、改過「這場以後」的系列（混合設定）時標頭與每列資訊正確、卡片（包含已額滿）與詳細頁標頭不同場時各自資料不混用。
- Playwright smoke：訪客在 `/classes` 看到合併後的卡、點進系列頁、挑日期進單堂頁；手機寬度檢查卡片與系列頁不橫向溢出。
- 品牌與 RWD：對照 `docs/harness/brand-review-checklist.md`、`rwd-checklist.md`；不使用斜體強調、01/02 編號標籤、monospace 標籤。

- `docs/product/route-map.md`：新增 `/classes/series/[recurringClassSeriesId]` 一列，並更新 `/classes` 的說明（持續開課也合併）。

## 7. 風險

| 風險 | 處理 |
|------|------|
| 既有 e2e 或測試以「逐場一張卡」為前提 | 開工前先 grep 受影響的測試，列入對應票的驗收 |
| 系列內場次的名額、設定被「改這場和之後所有場次」改成不一致 | 卡片與詳細頁標頭只用「下一堂」那場的資料，不用系列預設值；清單每列顯示自己的時間地點差異 |
| 截圖裡「秋季班」若其實是期班卻沒合併 | 實作前用本機資料庫確認它的 `kind`；若是期班，另開 bug 處理，不併進本計畫 |
| 持續開課場次很多時詳細頁變長、查詢變重 | service 查詢層只取 `show` 筆（預設 8、上限 200，只取必要欄位），不讀全部 |

## 8. 需要產品主人確認

- 新增一個公開路由（`/classes/series/[id]`）與其可見規則：已在 grill 中確認；實作前仍須在對應票的 Human Gate 放行。
