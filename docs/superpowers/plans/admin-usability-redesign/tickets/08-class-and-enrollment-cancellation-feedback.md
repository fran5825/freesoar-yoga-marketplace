# 08: 課程與報名取消確認及回饋

**What to build:** 管理員取消整堂課或單筆報名時，能辨識即將影響的課程／學員、確認實際後果，避免重複提交；失敗可依當下資格重試，成功遵守第一批已建立的不同返回流程。

**Blocked by:** None（第二批內無票券依賴；第一批返回機制與既有確認元件已存在，開工仍須符合共同 Human Gate）。

**Status:** accepted（2026-10-04 實作；2026-10-05 產品主人畫面驗收通過）

**Workflow mode:** STANDARD

**Human Gate:** yes（2026-10-04 產品主人已確認四票粒度與依賴並授權寫入文件；第一批畫面驗收及第二批 Builder 放行仍須另有紀錄）。

**Risk flags:** BRAND_RISK、LOW_PRESSURE_UX_RISK、SCOPE_DRIFT_RISK。僅調整既有取消的對象呈現、確認與回饋，不變更取消資格或報名規則。

**來源：** 管理後台第二輪規格與四批計畫的第二批；Q8、Q12、Q14、Q15、Q20，以及本次四票確認。

## Acceptance criteria

- [x] 整堂取消確認顯示課程名稱、連帶報名影響與不可恢復後果；單筆取消確認顯示課程與目前可讀的學員識別，以及不可恢復、同學員不可重報同一場的後果。
- [x] 不新增取消原因欄位、名單搜尋或新名單資料讀取；不提前加入第三批的 pending 取消入口或完整姓名／email 欄位。
- [x] 確認視窗可返回、Esc 關閉與回復焦點；關閉不送出。鍵盤與手機都能讀清對象／後果並完成操作，長名稱不溢出。
- [x] 確認送出後顯示處理狀態並停用重複操作；失敗時顯示對象、原因與可行下一步，不假稱成功，也不讓按鈕永久停用。
- [x] 仍由既有 server service 依當下狀態與開始時間判斷取消資格；資格已變時不可繼續提供無效取消操作，不以 UI 防連點取代 server 檢查。
- [x] 整堂取消成功回原課程搜尋／分類並可追查結果；單筆取消成功留同一課程名單並保留原詳情返回脈絡，無需重新尋找課程。
- [x] 原確認欄位、取消連帶效果、通知與不可重報規則不變；只描述既有通知效果，不新增 email 保證或通知能力。
- [x] desktop 1280px／mobile 390px 驗證整堂與單筆成功、取消確認、錯誤可重試、資格／時間變動與重複提交；若調整共用確認元件，回歸老師暫停。

## 實作紀錄（2026-10-04）

- 取消沒有需要保留的輸入，所以維持既有「失敗回同一課程詳情並重新載入」：重新載入後只會出現當下仍合法的取消操作，資格判斷仍完全由 server service 決定。
- 確認視窗：整堂取消顯示課程名稱、會一併取消的報名數（pending＋confirmed，與取消核心一致）與不可恢復；單筆取消顯示學員（名單既有的 `memberLabel`）、課程名稱、不可恢復與同學員不可重報。只沿用既有「學員會收到通知」描述，不新增 email 承諾。長名稱以 `wrap-anywhere` 換行。
- 回饋：成功／失敗訊息指出對象與下一步。整堂成功「課程已取消，已報名學員的報名也一併取消。」回原搜尋／分類並可追查；單筆成功「已取消「學員」的報名，同一位學員不能再報名這堂課。」留在同一課程名單與返回脈絡；失敗「課程沒有取消：…／「學員」的報名沒有取消：…畫面已更新為目前狀態，請確認後再操作。」學員識別以隱藏欄位帶入，只用來寫提示，不影響取消資格。
- 共用 `AdminConfirmButton`：未傳 `pending` 時改用 `useFormStatus` 追蹤所在表單送出，請求結束即解除停用，修掉「失敗跳回同頁後按鈕永久停用」；傳 `pending` 的老師暫停（票 07）不受影響，已回歸。
- 驗證：tsc、lint、build、diff check 通過；admin 全部 smoke＋`role-switch`＋`notification`＋`class-session-cancellation` 共 142 項，138 項首輪通過；4 項失敗發生在同一輪資料庫連線錯誤（`PrismaClientInitializationError`、auth adapter error）且整輪耗時約平常 3 倍時，重跑後通過（`admin-class-session-management.spec.ts:109` 另單獨 ×4 ×雙裝置 8/8）。新增「資格已變時取消失敗、提示對象與下一步、畫面更新、其他按鈕仍可用」測試。截圖 `.ai-runs/admin-usability/*-enrollment-cancel-confirm.png`。
- Codex peer review 第 1 輪指出：取消核心遇到資料庫暫時錯誤會直接拋出例外，不會回傳 `ok: false`；action 以 `withTransientFailure()` 只包住 service 呼叫，把例外轉成「系統暫時無法完成，可以稍後再試一次。」走同一失敗回饋（service、取消規則不變，redirect 不受影響）。
- 補兩個短測試：(1) 單筆與整堂各製造一次 server 端失敗（竄改隱藏欄位，資格不變所以按鈕留下），驗證同一顆按鈕解除停用並重試成功；(2) 攔住 server action 請求延遲回應，驗證按鈕顯示「取消處理中…」並停用、強制點擊不再送出，實際只送出 1 次請求，放行後成功。`admin-class-session-management`＋`admin-teachers` 52 項中 51 項通過，唯一失敗為老師搜尋長流程（高負載已知），單獨 ×3 ×雙裝置 6/6。
- 未驗證：資料庫例外本身沒有在 e2e 中真的製造（無注入點），只以程式碼確認 `withTransientFailure` 與其他失敗走同一路徑；`admin-class-session-management.spec.ts:109` 與老師搜尋測試是長流程，高負載時會逾時。
