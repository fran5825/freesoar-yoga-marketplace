# 老師流程與排版順手度整理計畫（2026-09-25 定案，2026-09-26 票 01–10 全部實作完成，等使用者驗收）

這份記錄 2026-09-25 跟 Franz 用 grill 方式討論出的決策。目標：老師從申請、建立課程到查看課程詳情，步驟更少、排版跟全站（含團主端）一致、一眼找得到下一步。

參考 `docs/organizer-usability-plan.md` 的做法（待處理提示、列表整張可點、詳情頁下一步放最上面）。

**範圍限制**：不動資料庫結構、不動狀態機、不動權限；不新增「編輯課程」功能；不動團主與管理員頁面；不動 V1 scope。

## 現況問題

- `/teachers/join` 申請表單是單頁 943 行長表單，頁寬 `max-w-5xl`，跟登入後頁面的 `max-w-4xl` 不一致；看不出還缺哪些欄位。
- 簡介、教學風格兩個必填長文字欄沒有範例，老師容易卡住。
- 審核中、被退回時仍顯示可編輯的申請表單，退回原因與需修正欄位不明顯。
- `/teacher/classes/new` 三種模式（單堂／每週／固定日期）平鋪，最常見的單堂沒有突顯；每次都要重填地點、人數上限。
- `/teacher/classes` 只有列表，**沒有單堂課詳情頁**；報名名單、待審報名、操作按鈕全塞在列表卡片內。只有系列課有詳情頁。
- 總覽只顯示申請狀態卡，沒有「待你處理」。

## 定案決策

| # | 決策 |
| --- | --- |
| 1 | 範圍：申請（`/teachers/join`、審核中／退回畫面、通過後首次進總覽）、開課（`/teacher/classes/new`）、查看課程（列表、單堂詳情、系列詳情、報名名單）、總覽待處理區塊。需求池、可授課時間、老師資料頁只做版面統一（標題、頁寬、卡片樣式），不改流程。 |
| 2 | 新增 `/teacher/classes/[classSessionId]` 單堂課詳情頁；列表卡片整張可點進去（比照團主課程頁）。頁面順序：下一步提示 → 報名狀況與名單 → 課程內容 → 發布／取消／完成等操作。不動資料庫結構。 |
| 3 | 申請表單維持單頁，分成數個卡片區塊；頂端顯示「還缺 N 項才能送審」；草稿機制不變（比照團主開需求表單）。頁寬統一為 `max-w-4xl`。 |
| 4 | 送審必填維持現有 7 項（顯示名稱、簡介、教學風格、年資、擅長、服務地區、授課形式），不縮欄位；其他欄位（證照、價格區間、照片連結、偏好）標示「通過後再補也可以」。 |
| 5 | 簡介與教學風格維持兩欄必填，加上範例文字與字數提示；不合併欄位（合併會動資料模型，另列 backlog）。 |
| 6 | 詳情頁只放現有操作：發布開放報名、取消、標記完成、確認／婉拒待審報名。**不新增編輯課程內容**（會動 `ClassSession` 規則與狀態機文件），列 `docs/backlog.md` 之後單獨討論。 |
| 7 | 總覽最上方「待你處理」，排序：① 待審報名 ② 被團主選定、待建課的回應 ③ 課程日期已過、尚未標記完成 ④ 草稿課程未發布。沒有時顯示「目前沒有待處理事項」。每項一行文案並連到對應頁面；未通過審核時改顯示申請狀態與下一步（沿用現有 `statusCopy`）。 |
| 8 | （2026-09-26 產品主人改決定：「可授課時間」併入「老師資料」成為第一個分頁，`/teacher/profile`＝可授課時間、`/teacher/profile/info`＝個人資料，舊網址 `/teacher/availability` 轉址；導覽列剩 5 項。通知改用各專區自己的網址 `/teacher/notifications`、`/organizer/notifications`，點通知不再跳到另一個專區。多重身分的切換入口交給管理員工作階段票 02。以下為原文）導覽列項目維持：總覽、需求池、我的課程、可授課時間、老師資料、通知；右側「＋ 建立課程」。不合併可授課時間。 |
| 9 | 審核中：申請頁改成唯讀摘要，不再顯示可編輯空表單。被退回：退回原因放頁面最上方、標出需修正欄位、按鈕跳到第一個缺項。不寫具體審核天數，只寫「審核完成後會在站內通知你」（寄 email 尚未實作，見 backlog 第 10 項，不可寫成會寄信）；有確定時效再補。 |
| 11 | 入口導向（2026-09-25 補，原 backlog 第 9 項併入）：已通過審核或已暫停的老師開 `/teachers/join`（含 header「老師合作」）直接導到 `/teacher/dashboard`；草稿、審核中、被退回、沒有老師資料者仍留在申請頁。header 連結不改，比照團主 `/organizers/request` 由頁面依狀態導向。**狀態對應表待產品主人確認後才動工。** |

## 需要注意的前置查證（動工前先做）

- 決策 7 ②「被團主選定、待建課」：先確認現行資料與流程是否能判斷（`DemandResponse` 為 `selected` 且尚未建立 `ClassSession`），查不到就先不放這一項並回報。
- 決策 10「上一次的選擇」：先確認不需要新增資料欄位；若只能靠新增欄位才做得到，改為讀取老師最近一堂課的值，或退回不做並回報。
- 決策 2：確認 `read-service.ts` 是否已有單堂課的 own-scoped 讀取；沒有的話新增讀取函式要走 service layer 並做老師本人權限檢查（涉及權限，動工前要做 security review）。

## 實作建議分批（每批做完由 Franz 看過畫面再下一批）

1. 版面統一：申請頁與各老師頁的頁寬、標題、卡片樣式（決策 1、3 的頁寬部分）
2. 申請表單區塊化、缺項提示、範例文字（決策 3、4、5）＋審核中／退回畫面（決策 9）
3. 單堂課詳情頁＋列表卡片整張可點（決策 2、6）
4. 開課表單預設與精簡＋建立後導向詳情頁（決策 10）
5. 總覽「待你處理」（決策 7）
6. 入口導向（決策 11，第 10 票；依賴第 2 批的審核狀態畫面）
