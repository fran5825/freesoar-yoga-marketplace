# ADR 0008: 通知記錄所屬課程系列，同系列的通知合併顯示

## Status

Accepted（2026-10-11，產品主人於 `/grill-with-docs` 核准方案 C 與 schema 變動；實作仍需逐票 Human Gate 與獨立測試資料庫）。

## Context

老師建立一個 8 堂的期班（或生成更多場次），會收到 8 則內容一模一樣的「課程已建立」通知與 8 封 email；取消整個系列或從某場以後全部取消，也是逐堂發送。（修改整個系列目前已經是每位受影響學員一則。）通知頁一則一張卡，同一件事被拆成好幾張，真正的新消息被淹沒。`Notification` 目前只記類型、標題、內文與可選的單筆目標（`targetType`／`targetId`），沒有任何欄位能分辨「這幾則屬於同一個系列」。

產品主人希望「同類型、同系列的通知只顯示一則」，而且這個原則要套用到整個網站（老師、團主、學員共用同一個通知頁）。

## Decision

- `Notification` 新增**可為空**的 `recurringClassSeriesId` 與索引。課程相關的通知（建立、異動、取消、完成、報名相關）在該課屬於系列時寫入系列 ID；其他通知為 `NULL`。外鍵在系列被刪除時設為 `NULL`（`onDelete: SetNull`），與 `ClassSession.recurringClassSeriesId` 一致。
- **批次動作從源頭只發一則**：建立系列、生成更多場次、取消整個系列、從這場以後全部取消（修改整個系列已是一人一則，只補系列 ID 與堂數文字），每位收件人只發一則站內通知與一封 email，內文寫堂數與日期範圍。
- **顯示時再合併**：同一位收件人、同類型、同系列、同一天（台北時間）的通知顯示成一則，標示則數與最新時間。用來收「老師一堂一堂分開操作」產生的多則通知。（2026-10-24 補充，teacher-first-run 票 10 review：合併條件再加上「標題相同」。同一類型可能有不同說法，例如老師收到的 `enrollment_cancelled` 分成「有學員取消報名」「有學員請假」「有學員退出整期」；標題不同的不合併，避免用最新一則的標題蓋掉其他事件。這裡比對的是同系列內的標題，不是上方選項 B 那種跨課程的文字比對。）
- 舊通知不補系列 ID，維持原樣顯示（目前沒有正式上線，舊的重複通知屬於測試資料）。

## Alternatives considered

1. **A：只改源頭，批次動作只發一則**：不動 schema，但老師分開操作的多則通知仍無法合併，也無法依系列連到系列頁。
2. **B：A 加上顯示時用「同類型、同標題、同一分鐘」判斷合併**：不動 schema，但靠文字比對，標題相同的不同課會被誤合併，時間窗也難定。
3. **用「批次 ID」取代系列 ID**：只能合併同一個動作產生的通知，產品主人要的是「同系列」，跨動作仍會重複；也無法提供連到系列頁的資訊。
4. **不限時間、同系列同類型永遠合成一則**：一個月後的新事件會被舊的那則蓋住，看不出有新消息，所以加上「同一天」。

## Consequences

- 一個 additive migration（新欄位與索引），不改寫既有資料；`docs/domain/data-model.md` 需在同一張票同步更新。
- 所有發課程相關通知的地方都要帶系列 ID，漏帶的只會變成「不合併」，不會出錯；要以測試涵蓋每個發送點。
- 批次動作的通知內容與 email 樣板要改成「共 N 堂」的版本；單堂動作維持原樣。
- 合併後的通知依身分連到系列頁（老師：系列管理頁；學員：期班頁或系列頁）。
- 未來若要做「已讀／未讀」，合併的一則要定義成「其中任一則未讀就算未讀」。
